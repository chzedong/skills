# 解构技术对象 — 生成系统性学习 HTML 文档

帮助开发者深度学习任何技术对象：开源库、框架、工具、概念、范式、协议、标准、设计模式。文档必须同时回答「怎么用」和「为什么这样设计」，支持从 5 分钟概览到深度钻研的分层阅读。

## 目标用户

前端/全栈开发者，希望通过一份文档：
1. **快速建立直觉** —— 这是什么、解决什么问题、最小示例怎么写
2. **掌握用法边界** —— 什么时候用、什么时候不用、常见坑
3. **理解深层原理** —— 内部如何工作、关键设计决策、如果我来写会怎么做
4. **连接知识网络** —— 与相关概念/库/协议的关系

## 可解构对象分类

根据用户输入判断对象类型，后续分析框架随之调整：

| 类型 | 例子 | 关注重点 |
|------|------|---------|
| **Library / Tool / CLI** | jotai、vitest、lark-cli | 用法 + 源码 + 工程化 + 架构 |
| **Framework / Platform** | tiptap、langchainjs | 生态位 + 扩展机制 + 核心抽象 |
| **Concept / Pattern** | Proxy、不可变数据、原子状态 | 定义 + 问题背景 + 典型实现 + 变体 |
| **Paradigm / Methodology** | 响应式编程、函数式编程、TDD | 思想起源 + 核心原则 + 语言/框架映射 + 适用边界 |
| **Protocol / Standard** | HTTP/2、OAuth、ESM、WebRTC | 规范动机 + 交互流程 + 关键字段/状态机 + 实现差异 |

## 双线内容模型

每篇文档必须同时包含两条线，用视觉组件区分：

**用法线（What & How）**
- 一句话定义
- 最小可运行示例（3-5 行）
- 2-3 个常见使用场景
- API / 配置速查
- 最佳实践
- 踩坑与反模式
- 与同类方案对照

**原理线（Why & How it works）**
- 它解决了什么问题
- 核心思想 / 心智模型
- 内部数据结构、流程与算法
- 关键代码引用（路径:行号 + IDE 跳转，库/框架类对象适用）
- 设计权衡与决策
- 历史演进
- 「如果我来写」对比思考

## 渐进式阅读深度 L1-L4

在文档开头给出阅读路径，正文中每个 section 用 `data-level` 标记默认深度：

| 层级 | 耗时 | 目标 |
|------|------|------|
| L1 概览 | 5 min | 知道是什么、解决什么问题 |
| L2 上手 | 30 min | 能写最小示例、了解常见用法 |
| L3 深入 | 2 h | 理解核心原理、能读关键源码/规范 |
| L4 精通 | 长期 | 能改造、能讲清设计决策 |

## 触发条件

用户消息中包含以下意图之一时触发：
- "分析"/"解构"/"解读"/"学习" + 开源库/项目/仓库/概念/范式/协议
- "帮我理解"/"帮我看看" + 技术对象名
- "生成"/"写" + 项目文档/学习文档/HTML文档/技术解析
- 提供本地仓库路径并要求生成解释文档
- "这个库是怎么设计的"/"这个项目的架构"/"这个概念是什么意思"

## 核心原则

1. **用法与原理并重**：不要只贴源码，也不要只写教程；两者相互印证。
2. **问题驱动**：先讲「为什么需要它」，再讲「它是什么」。
3. **可验证**：代码引用必须带文件路径和行号；规范引用必须带章节/链接。
4. **可分层**：每个主题从 L1 到 L4 自然递进，允许读者跳过不感兴趣的深度。
5. **知识连接**：用概念图谱、对照表把当前对象与相关技术联系起来。
6. **诚实边界**：不确定的内容标注「推测」，不要编造。

## 输出产物

- 一个或多个结构化的 HTML 文件，可本地浏览器打开阅读。
- 默认输出到 `chzedong.github.io/<对象名>/`。
- 大型对象采用「索引页 + 模块子页面」结构。

├── Section 1: 项目/概念背景（问题驱动）
├── Section 1.5: 快速上手 ⭐（最小示例 + 常见场景）
├── Section 2: 用法详解
│   ├── API/配置速查

├── Section 3: 工程化方案（Library/Framework 适用）
├── Section 4: 项目制品/生态（Library/Framework 适用）
├── Section 5: 核心原理
│   ├── 心智模型
│   ├── 数据流/状态机/交互流程
│   ├── 关键代码/规范引用
│   └── 算法与数据结构（如适用）
├── Section 6: 架构设计（Library/Framework 适用）
│   ├── 模块划分
│   ├── 设计模式

## 按类型调整分析重点

### Library / Tool / CLI
- 读取 README、package.json、源码结构、测试用例
- 入口识别、核心链路追踪、代码引用
- 工程化工具链、CI/CD、发布策略

### Framework / Platform
- 核心抽象与扩展点
- 生态位：与同类框架的差异
- 插件/中间件/适配器机制

### Concept / Pattern
- 精确定义与起源
- 解决了什么具体问题
- 典型代码实现（多种语言/库可选）
- 常见变体与误用

### Paradigm / Methodology
- 思想背景与历史
- 核心原则（3-5 条）
- 在主流语言/框架中的体现
- 适用场景与组织成本

### Protocol / Standard
- 规范动机与解决的问题
- 角色与时序图
- 关键字段/状态机/报文格式
- 主流实现差异与安全注意

## Source 来源

根据对象类型选择合适来源：

| 类型 | 来源 |
|------|------|
| Library | README、源码、package.json、测试、GitHub commits/issues/releases |
| Framework | 官方文档、源码、生态插件、RFC/ADR |
| Concept | MDN、维基、经典博客、实现库源码 |
| Paradigm | 论文、书籍章节、语言特性文档、框架实现 |
| Protocol | RFC/规范、官方文档、Wireshark/抓包、参考实现 |

## 关键约束

- **输出与部署**：HTML 文件必须生成到 `chzedong.github.io/<对象名>/` 目录下。生成完成后自动执行 `git add . && git commit -m "docs: deconstruct <对象名>" && git push origin main`（推送前设置代理环境变量）。
- **只读操作**：分析过程只读取仓库/文档/规范，不修改任何外部内容。
- **快速上手优先**：深度分析前提供 3-5 行最小可运行示例 + 2-3 个常见场景示例。
- **图表用 Mermaid**：复杂流程图 / 架构图 / 依赖图 / 时序图使用 `<pre class="mermaid">` 嵌入，每个图下加说明 caption。
- **代码引用规范**：每次引用代码必须标注文件路径和行号，格式 `src/core/store.ts:42-68`；核心代码段提供 IDE 跳转链接（`vscode://file/<absolute-path>:行:列`）。
- **规范引用规范**：引用 RFC/规范时标注章节号或链接。
- **「如果我来写」对比**：每个核心模块/概念至少一个直觉做法 vs 实际做法的对比框。
- **关键决策提取**：从历史资料中提取 3-5 个有教学价值的技术决策，标注版本号/时间和原因。
- **准确性**：不确定的内容标注「推测」，不要编造。

## HTML 组件使用指南

生成 HTML 时优先使用以下组件（样式见 template.html）：

- `<span class="badge badge-primary">Concept</span>` —— 对象类型徽章
- `<div class="level-tabs">...</div>` —— L1-L4 深度入口
- `<div class="mental-model">...</div>` —— 心智模型框
- `<div class="callout callout-insight">...</div>` —— 「如果我来写」对比
- `<div class="callout callout-tip">...</div>` —— 最佳实践
- `<div class="callout callout-warning">...</div>` —— 踩坑/反模式
- `<div class="decision-box">...</div>` —— When to use / When NOT to use
- `<table class="comparison-table">...</table>` —— 同类对比矩阵
- `<pre class="mermaid">...</pre>` —— 流程/架构/概念图谱
- `<dl class="glossary">...</dl>` —— 术语表
